# Boros real account / hypothetical scenario and Zerion refresh — 2026-10-04

## Delivered

- The pre-entry panel has explicit real-account and hypothetical modes. Real budget is the positive available margin of the selected collateral and cross/isolated account, converted at the account asset's current price. It is neither cash nor total equity across collateral zones. Missing/stale balances cannot fall back to manual money. Withdrawal updates live budget and invalidates old results. Switching to hypothetical retains independent manual capital.
- Real opportunities are restricted to compatible collateral. In isolated mode the existing selected market account is used; cross cash is not silently assumed transferred into an isolated market. Allocation and the maximum loss in the adverse modeled scenario filter candidates; this is not a guaranteed loss cap or probability of profit.
- Up to three ranked candidates are simulated sequentially through the existing read-only official endpoint. Failed/unfilled/unknown-margin quotes and estimates outside the specified scenario budget are discarded. The rate from the quote is used for projected settlements; post-order total margin minus existing margin is used for the approximate remaining budget, avoiding a second subtraction of existing margin. Ranked profits still depend on manually declared fees/gas/other slippage and the future floating-rate assumption. Common cost assumptions across markets are not official market-specific fee quotations. Unknown costs or insufficient funding history block recommendations.
- No analytical single-position liquidation rate is presented as real cross-account liquidation. Real mode shows the official preview's nullable APR only. Quotes expire after 60 seconds and are invalidated by changes in account, collateral, positions/orders, size, direction, market or margin mode. Unavailable liquidity, or available but insufficient indicative liquidity, cannot be a verified opportunity.
- The assistant receives per-collateral cash/equity/initial/free margin/maintenance buffer, collateral prices and gas credit, as well as positions, orders, settlement PnL and the selected preview/candidate. Account-bound derived insights use an internal scope (never sent to Gemini) based on balances/positions/orders; mismatched prior-account/withdrawal results are omitted. Hypothetical insights remain explicitly simulation data and expire separately. Recommendation calculation is deterministic; Gemini explains rather than guarantees or executes it.
- Official candidate scanning currently runs from the real pre-entry panel after the user supplies costs/risk/allocation; the assistant consumes that result. It does not autonomously execute tools or scan every account/market from a chat alone without cost assumptions. Public 1000-dollar reference calculations remain labelled reference analysis.
- Zerion freshness adapts to remaining organization day/month quota: normal balance 30 minutes, reduced budget 60 minutes, critically low budget 4 hours; transaction/chart cache at least 60 minutes. Provider timestamps remain unchanged and stale labels remain truthful. No extra account/key rotation scheme is used.
- Background portfolio and extra Arcus-wallet balance loaders no longer poll transaction history. Visible activity still obtains history on demand with hourly dedup. A lightweight authenticated wallet-event revision check (our cache, no Zerion request) invalidates only the affected wallet, refreshes existing history, deduplicates mounted consumers and ignores responses after logout. Activity-triggered refreshes also respect the reduced quota interval so notification bursts cannot bypass budget backoff. Cross-instance activity/cooldown reads bypass local cached versions.
- Signed webhook receiver is routed to the existing integrations function to stay within the 12-function deployment limit. It pins an independently supplied trusted public certificate, verifies exact raw-body RSA-SHA256 and timestamp, accepts only configured public wallets, ignores spam, deduplicates confirmed events separately from rollbacks and persists invalidation before acknowledging. It never fetches a certificate URL supplied by an attacker, stores private credentials or applies prices/balances from webhook payloads. Persistent cache failure returns a retryable error. Periodic reconciliation remains the fallback.

## Activation remaining outside the code

Changes are not deployed. For webhook delivery, Zerion requires production callback URL whitelisting. Request approval for the production `/api/zerionWebhook` URL, obtain the authentic Zerion public certificate through a trusted source, and configure server variables:

- `ZERION_WEBHOOK_CERTIFICATE_PEM`: authentic public PEM certificate (not a wallet/API private key).
- `ZERION_WEBHOOK_WALLETS`: comma-separated watched public addresses; the setup helper supports up to five for one free subscription.
- `ZERION_WEBHOOK_CALLBACK_URL`: approved HTTPS URL used by the registration helper.

After deployment/approval, run `node scripts/register-zerion-webhook.mjs` in a trusted environment with the server variables. It first checks for an existing callback to avoid duplicate creation and does not print keys. It has not been run against the user's real Zerion organization. Certificate rotation requires updating the pinned public PEM. The app's existing Neon providerCache table must be available; no migration is introduced. A webhook is not guaranteed delivery and does not include prices; it cannot grant additional daily/monthly quota or replace a periodic full reconciliation.
